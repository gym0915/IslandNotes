# 当前便签工作台与便签库｜Throwaway UI Prototype

> **PROTOTYPE — 仅用于 HITL 交互方向评审，不是生产代码，也不应直接并入正式 App。**

要回答的问题：当前便签编辑器、挂起 / 取消挂起、入库、删除、字符进度、便签库入口和点击交换，应该采用哪一种页面结构，才足够清晰且不互相干扰？

## 一个命令运行

在项目根目录执行：

```bash
python3 -m http.server 4173 --directory "docs/prototypes/current-note-workbench"
```

打开：

- 总入口：<http://localhost:4173/?variant=A>
- A「聚焦画布」：<http://localhost:4173/?variant=A>
- B「工具轨道」：<http://localhost:4173/?variant=B>
- C「编辑台账」：<http://localhost:4173/?variant=C>

URL 的 `variant` 参数可分享，刷新后仍保持当前方案。业务状态只存在内存里，刷新会恢复为“空白当前便签 + 四条样例旧便签”。原型不发起任何网络请求。

## 三种方向

| 方案 | 信息层级 | 主要操作位置 | 便签库进入方式 |
| --- | --- | --- | --- |
| A 聚焦画布 | 当前文字占据绝对中心，状态和容量退到编辑器底部 | 屏幕内底部三段动作坞 | 顶部右侧的紧凑入口 |
| B 工具轨道 | 当前便签与动作并列，挂起状态在编辑区上方 | 左侧永久纵向工具轨道 | 从屏幕底部“抽出”便签库 |
| C 编辑台账 | 先看命令与状态规则，再进入带基线的编辑区 | 顶部横向命令区 | 左上角“便签目录”侧页入口 |

三套方案共享同一套内存状态转移，仅页面骨架不同。底部中央的黑色切换器和可折叠 `STATE INSPECTOR` 都只供评审，不属于产品 UI。除 textarea / input / contenteditable 聚焦时外，可用键盘 `←` / `→` 切换方案。

## 可复现评审路径

对 A、B、C 各走一遍：

1. 刷新页面，确认当前便签为空白，没有“新建”按钮，挂起 / 入库 / 删除均禁用。
2. 输入中英文、手动换行与 Emoji，例如：`Call Mom / 给妈妈回电话 👩‍👧‍👦`，观察“正在自动保存”到“已自动保存”。
3. 点击圆形进度，核对“已输入 / 还可输入”；粘贴超过 240 个用户感知字符的内容，确认只保留 240 个并出现轻提示。
4. 挂起，再取消挂起；重新挂起后继续编辑，确认仍保持挂起。
5. 挂起状态下放入便签库，确认自动取消挂起、库顶部新增该便签、当前槽位为空白。
6. 输入新便签，点删除；先取消确认，再次删除并确认，检查当前槽位为空白。
7. 输入一条当前便签并挂起，进入便签库，点任一旧便签；确认先取消挂起、旧当前便签进入库首、所点便签成为当前便签。
8. 在便签库确认只有“点击交换”，没有编辑、挂起或删除入口。
9. 切换浅色 / 深色；展开 `STATE INSPECTOR` 核对 `currentNote`、`isPinned`、`library`、`characterCount`、`recentAction`。
10. textarea 保持聚焦，按左右方向键，确认光标移动而不是切换方案；失焦后再按，确认方案会切换。
11. 刷新页面，确认业务状态重置，但 `?variant=` 保持。

## 样例覆盖

初始便签库包含：中文与时间、英文完整句、手动换行、组合 Emoji，以及一条接近 240 字符的中英文混排长便签。便签库按 `addedAt` 最近优先；每次入库或交换进入库的原当前便签都会成为第一条。

## 明确不做

无持久化、网络请求、数据库、账号、iCloud、通知、Live Activity、灵动岛或锁屏视觉、生产级错误处理。原型中的“挂起”和“自动保存”都只是内存状态反馈。
